# 平台包与迁移说明（0.2.0）

五个平台包共用同一套会话语义与错误码。Android、iOS、macOS、Windows x64 均由 [`native/`](../native/) 中的同一份 C/C++ 核心编译生成；Web 包为 `@apexo/sdk`（[`web/`](../web/)）。

模型权重文件不打进 SDK 包内，由宿主应用按需部署在本地路径或同源/CORS URL。

## 引擎加载与路径规则

原生默认引擎通过动态加载绑定 `sherpa-onnx` 与 `LiteRT-LM`：

1. 可在 `apexo_engine_state_create` 之后、首次 `push_pcm` 或 `summarize` 之前调用 `apexo_engine_state_set_libraries(state, sherpa_path, litert_path)`（Java 为 `session.setLibraries(sherpaPath, litertPath)`）显式指定库路径。
2. 未显式指定时读取环境变量 `APEXO_SHERPA_LIBRARY` 与 `APEXO_LITERT_LIBRARY`。
3. 均未设置时按平台默认库名查找：
   - **macOS / iOS**：`libsherpa-onnx-c-api.dylib`、`libsherpa-onnx.dylib`、`@rpath/SherpaOnnxC.framework/SherpaOnnxC`；以及 `liblitert-lm.dylib`、`liblitert_lm.dylib`、`@rpath/CLiteRTLM.framework/CLiteRTLM`。
   - **Android / Linux**：`libsherpa-onnx-c-api.so`、`libsherpa-onnx.so`；以及 `liblitert-lm.so`、`liblitert_lm.so`。
   - **Windows x64**：`sherpa-onnx-c-api.dll`、`sherpa-onnx.dll`；以及 `litert-lm.dll`、`litert_lm.dll`。默认库名会优先在 `apexo_session.dll` 自身所在目录查找（与 macOS `@loader_path` 一致），再回退系统默认搜索路径；当加载包含目录的 DLL 路径时，先将 `/` 规范化为 `\` 并使用 `LoadLibraryExW(..., LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS)` 解析同目录依赖 DLL（如 `onnxruntime.dll`、`onnxruntime_providers_shared.dll`），若需从 `PATH` 查找运行库则回退 `LOAD_WITH_ALTERED_SEARCH_PATH`。`sherpa-onnx-c-api.dll` 与 `onnxruntime.dll` 为动态 MSVC 运行时构建，全新 Windows 系统需已安装 Microsoft Visual C++ 2015–2022 Redistributable (x64)（`vc_redist.x64.exe`）。Windows 模型路径优先传入 UTF-8 窄字符路径（匹配 `sherpa-onnx` 与 `litert-lm` 内部的 `CP_UTF8` 宽字符转换），并保留 ANSI/8.3 短路径回退，包含中文字符的模型目录不会因代码页有损转换而静默变成 `?`。
4. **纯文字总结模式**：创建引擎或会话时，`asr_model_dir` 可传 `NULL` 或 `""`，调用 `apexo_session_summarize_text` / `summarize(text)` 时不会加载 `sherpa-onnx`。

## iOS 接入与音频线程注意事项

- 将 `dist/ios/` 下的 `ApexoSession.xcframework`（静态库）、`SherpaOnnxC.xcframework` 与 `CLiteRTLM.xcframework`（动态 framework，需勾选 **Embed & Sign**）加入 Xcode 工程。
- `AVAudioEngine` 的 `installTap` 回调运行在实时音频线程上：宿主应像 [`ios-demo/ApexoDemo/MicCapture.swift`](../ios-demo/ApexoDemo/MicCapture.swift) 那样，在 tap 回调内仅复制 `AVAudioPCMBuffer` 并异步派发到串行队列（`audioQueue`）中执行 48 kHz → 16 kHz 重采样与 `apexo_session_push_pcm`，绝不在实时音频回调内执行首次模型加载、文件状态检查或锁等待。

## 从 0.1.0 升级到 0.2.0 的迁移说明

1. **`summarize()` 只读取已定稿的 `final`**：不再强行将未说完的 `interim` 定稿。若需在停止录音后生成包含最后一句的完整总结，请先调用并等待 `endSegment()` 完成尾帧刷写，再调用 `summarize()`。
2. **Web 总结与收尾统一为异步 Promise**：Web 端 `await session.endSegment()`、`await session.summarize()`、`await session.summarizeNew()`、`await session.summarize(text)` 均返回 Promise，失败时抛出带 `err.code`（`-3`/`-4`/`-5`/`-6`）的 `Error`，请使用 `try / catch` 处理，不再通过判断返回值是否为负数区分失败。
3. **总结运行期间不再拒绝 `push_pcm`**：`gemma_resident == 1` 期间继续调用 `push_pcm` / `pushPcm` 会正常返回 `0` 并进入 ASR，是否暂停录音由宿主应用自行决定。请注意边录边总结时 ASR 与 Gemma 权重会同时占用内存。
4. **新增纯文本总结入口**：C `apexo_session_summarize_text(session, text, out, out_cap)`、Java `session.summarize(String text)`、Web `await session.summarize(text)` 用于总结外部文本，不会加载 ASR 也不会修改会话内的 `full_transcript` 或 `summary_text`。
5. **区分阶段摘要与最终总结**：录音中途使用 `summarizeNew()` 追加阶段摘要；录音结束后使用 `summarize()` 执行跨块汇总归纳并生成最终会议总结。
6. **并发总结返回 `APEXO_ERR_BUSY (-6)`**：同一会话已有总结在运行时再次发起总结返回 `-6`（不再混用 `-5`）。
7. **新增 `reset()` 与转写事件回调**：清空当前会话推荐使用 `apexo_session_reset` / `reset()`（`release()` 作为兼容别名保留）；可通过 `apexo_session_set_transcript_callback` / `setTranscriptListener` / `onTranscript` 监听实时转写事件。
8. **`summarizeWithGemma()` 降级为兼容包装**：Web 新代码请直接调用 `await session.summarize()`；`summarizeWithGemma()` 保留成功时返回 `{ litert, summary }` 的兼容形态，内部复用同一总结路径，失败同样抛出带 `code` 的 `Error`。
9. **自定义 `ApexoEngines` 重新编译**：`0.2.0` 在 `ApexoEngines` 末尾新增了可选的 `asr_finish` 回调字段，请零初始化 `ApexoEngines`（如 `ApexoEngines engines{};`）并基于 `0.2.0` 头文件重新编译。
